## 1. 서비스 개요

고등학교 1학년 통합과학2 수행평가를 게임 형태로 만든 웹앱입니다. 두 층으로 되어 있습니다.

- **성적에 반영되는 층**: 단원별 과제(챕터). 학생이 문제를 풀고 서술형을 쓰면 서버가 채점해서 통과 여부와 점수를 기록합니다. 교사는 그 기록을 보고 최종 점수를 확정합니다.
- **동기 부여용 게임 층**: 연구포인트(rc)라는 재화로 조수를 뽑고(가챠), 강화하고, 연구동에 배치해서 포인트를 벌고, 연구실 테마를 삽니다. 랭킹도 있습니다.

두 층이 연결돼 있습니다. 과제를 풀면 연구포인트를 받고, 그 포인트로 게임을 합니다.
**그래서 게임 재화를 조작할 수 있으면 성적 관련 기록도 건드릴 수 있는 구조**라, 재화 로직도 성적만큼 엄격하게 봐야 합니다.

### 배포

## 3. 핵심 설계 — 반드시 이해하고 검증에 들어가 주세요

### 3-1. 서버 권위 원칙
학생 브라우저는 신뢰하지 않습니다. 개발자도구로 자바스크립트 변수를 바꿔도 성적과 재화가 흔들리면 안 됩니다.

- 연구포인트가 오르내리는 모든 경로는 `SECURITY DEFINER` 함수를 거칩니다. 클라이언트는 "얼마를 벌었다"고 보고하지 않고, "이 행동을 했다"고만 말합니다. 금액은 서버가 처음부터 다시 계산합니다.
- 채점도 마찬가지입니다. 정답은 서버 밖으로 나가지 않습니다. `lab_grade_round(라운드, 답)`이 참·거짓만 돌려줍니다.
- 클라이언트의 `S` 객체(로비 상태)는 `lab_state_sync`로 서버에 저장되지만, **보호 항목(rc, 조수 목록, 테마 등)은 서버가 기존 값이나 안전한 기본값으로 강제로 덮어씁니다.** 클라이언트가 보낸 값을 쓰지 않습니다.

**검증 포인트:** 보호 항목 목록이 실제로 빠짐없는지 확인해 주세요. 새로 추가된 상태 항목이 목록에서 빠지면 그대로 위조 통로가 됩니다.

### 3-2. 세션 모델
- `lab_students.session_token` / `session_at`. 한 계정은 한 기기에서만 접속합니다.
- `lab_session_timeout_minutes()` = **1분**. 마지막 활동에서 1분이 지나면 다른 기기가 세션을 가져갈 수 있습니다.
- 클라이언트는 20초마다 `lab_session_heartbeat`를 보내 세션을 살려둡니다. 로비와 챕터 페이지 양쪽에 있습니다.
- 만료 시각을 서버가 검사하지는 않습니다. 토큰이 일치하는지만 봅니다.

**검증 포인트:** 하트비트가 끊기는 화면이 남아 있는지(예: 특정 모달이 오래 열려 있는 경우), 그 상태에서 제출이 거부되지 않는지 봐 주세요.

### 3-3. 채점 흐름 (가장 중요)
```
학생이 제출
  → roundengine.js: submitSession()
  → syncToSupabase() → lab_submit_chapter(이름, 토큰, 단원, 모드, 라운드ID들, 답안, 시간 지표)
  → 서버가 lab_chapters에서 그 단원 원본을 읽음
  → 채점 대상 문항 수(expected_n)를 서버가 직접 셈 (클라이언트가 보낸 목록이 아님)
  → 각 라운드를 lab_grade_round로 채점, expected_n개까지만
  → 서술형은 클라이언트 목록을 무시하고 서버가 그 단원의 opinion 라운드를 전부 훑음
  → 통과 여부·점수·크레딧 확정 → lab_submissions에 기록, lab_game_state의 rc 갱신
  → 결과를 클라이언트에 반환 → 결과 화면과 로비 기록을 서버 값으로 다시 그림
```

**여기서 과거에 사고가 났던 지점 세 가지 (전부 수정됨, 재발 여부를 봐 주세요):**
1. 분모를 클라이언트가 정하면 맞힌 문제만 골라 내서 합격을 위조할 수 있습니다.
2. 서술형 문항 목록을 클라이언트가 정하면 빈 목록을 보내 자동 통과할 수 있습니다.
3. 문제풀 전체를 한 번에 제출하면 점수가 최대치를 넘고(예: 27/6) 크레딧을 한꺼번에 쓸어갈 수 있습니다.

### 3-4. 클라이언트/서버 데이터 스키마 정합
`lab_game_state.data`(jsonb)에 들어가는 항목은 클라이언트 네 곳에 전부 나타나야 합니다.
- `S` 초기값 리터럴
- `applyStateSnapshot()` — 서버 값을 클라이언트로 옮김
- `saveLabState()` — localStorage 저장
- `gameStateSyncPayload()` — 서버로 보낼 값 구성

**한 곳이라도 빠지면 그 항목은 저장은 되는데 다음 접속 때 사라집니다.** 실제로 이 문제로 조수가 사라지는 사고가 있었습니다.
현재 17개 항목이 네 곳 모두에 있는 것을 확인했지만, **직접 다시 세어봐 주세요.**

### 3-5. 챕터 데이터의 함정
`chapterdata.js`는 화면을 그릴 때 `itemsVar`(변수에서 항목을 꺼냄), `correctValue`(계산 결과와 비교), `{{변수}}`(숫자 치환)를 해석합니다.
**그런데 서버는 원본만 봅니다.** 그래서 정답 정보가 화면 렌더링 시점에 생기는 문항은 서버가 채점할 수 없고, 학생이 정답을 써도 무조건 오답 처리됩니다.

12단원 1번과 17단원 3번이 이 문제였고, 정답을 문항 안에 직접 넣는 형태로 고쳤습니다.
`lab_chapter_save`에 검증을 넣어 앞으로 이런 문항은 저장 자체가 거부됩니다.

**검증 포인트: 나머지 10개 단원에 같은 형태의 문항이 더 있는지 전수 확인해 주세요.** 이게 가장 도움이 될 작업입니다.

### 3-6. Postgres 함수 오버로드 함정 (이 프로젝트에서 실제로 크게 데였습니다)
`create or replace function`은 **매개변수 개수가 다르면 기존 함수를 대체하지 않고 새 함수를 하나 더 만듭니다.**
세션 검증(`p_token`)을 추가하면서 매개변수가 하나 늘었는데, 옛 버전 다섯 개가 그대로 살아남아 계속 호출되고 있었습니다.
그 결과 데이터 초기화를 여러 번 해도 학생 브라우저의 낡은 캐시가 세션 검증 없는 옛 함수를 통해 되살아났습니다.

지금은 전부 삭제했고 스키마에 방어용 `drop function`을 넣었습니다.

**검증 포인트:** 아래 쿼리가 빈 결과를 돌려주는지 확인해 주세요. 하나라도 나오면 심각한 상태입니다.
```sql
select proname, count(*) from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace
 where n.nspname='public' and proname like 'lab\_%'
 group by 1 having count(*) > 1;
```

## 5. 아직 안 본 곳 / 우선순위 제안

직전 점검은 **재화와 채점의 위조 경로**에 집중했습니다. 아래는 손이 덜 간 영역입니다.

**높음**
1. **나머지 10개 단원의 문항 전수 검사** (3-5절). 서버가 채점 못 하는 문항이 더 있으면 학생이 정답을 써도 오답이 됩니다. 성적에 직결됩니다.
2. **`teacher.html` 전체.** 이번에 거의 안 봤습니다. 교사 비밀번호 취급, 명단 관리, 문항 편집이 학생 데이터를 망가뜨릴 여지가 있는지 봐 주세요.

## 6. 검증하는 법

### 실행 환경
- Node.js가 설치돼 있지만 PATH에 없을 수 있습니다.
- Windows + git bash 환경에서 한글이 깨지므로, **`node -e "..."`나 `curl -d`에 한글을 직접 넣지 마세요.** 파일로 써서 `node 파일.js` 또는 `curl --data-binary @파일`로 넘기세요.
- `URL`을 변수명으로 쓰면 Node의 전역 `URL`을 가려서 `fetch`가 깨집니다.

### 자격 증명
- **anon key**: `supabase-config.js`에 있습니다. 공개되는 값이라 그대로 쓰면 됩니다. 학생과 같은 권한입니다.
- **Management API PAT**: 스키마를 직접 실행하거나 DB를 조회할 때 씁니다. `~/.claude/secrets/.env`의 `SUPABASE_PAT`에서 읽으세요. **화면·파일·커밋에 절대 노출하지 마세요.** 없으면 선생님께 요청하세요.
  ```
  POST https://api.supabase.com/v1/projects/oqhldrkmcewcjslciqmp/database/query
  Authorization: Bearer <PAT>
  body: {"query": "..."}
  ```
- **교사 비밀번호**: 선생님께 직접 받으세요. 파일에 적지 말고 환경변수로 넘기세요.

### 준비된 스크립트 두 개
같은 폴더에 있습니다. 둘 다 테스트 계정 `zz_공격테스트`(초기 비밀번호 `8888`)만 건드리고, 끝나면 흔적을 지웁니다.

```bash
# 공격 시나리오 11가지가 실제로 막혔는지 (현재 11/11 통과)
TEACHER_PW=<선생님께 받은 값> node 검증스크립트_공격시나리오.js

# 정상 플레이 한 바퀴가 되는지 (로그인→동기화→하트비트→테마→정답 제출→서술형 저장)
node 검증스크립트_정상플레이.js
```

주의: 공격 스크립트는 검증 동안 로그인 권한을 잠시 열었다가 **끝나면 다시 닫습니다.**
중간에 멈추면 학생들이 로그인을 못 하니, 반드시 아래를 실행해서 열어두세요.
```sql
grant execute on function public.lab_login(text,text) to anon, authenticated, public;
```

### 점검 모드
큰 수정을 하는 동안 서비스를 닫으려면 두 파일의 플래그를 켜고 push하면 됩니다.
```
shinjang_science.html : const MAINTENANCE_MODE = true;
roundengine.js        : const MAINTENANCE_MODE = true;
```
학생들에게 "점검 중입니다" 안내만 보입니다. 확실히 막으려면 위 `grant`의 반대인 `revoke`도 함께 하세요.
